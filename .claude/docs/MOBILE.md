## 1. What this workspace is

A **Capacitor 8 container** ([#524](https://github.com/zelytra/Librarius/issues/524)). Beyond
`capacitor.config.ts`, `tsconfig.json` and
`package.json`, it also holds `android/` — the native Android project, generated by
`cap add android` and committed since [#70](https://github.com/zelytra/Librarius/issues/70)
(§ 7 explains why committed rather than regenerated). None of it is application code in the
usual sense: **no React code, no screen, no style** anywhere in this workspace. The
application that runs inside the container is `apps/web`, exactly the bundle the browser
gets — `android/` is packaging around that bundle, not a second copy of the app.

What is deliberately **not** here yet:

- `apps/mobile/ios/` — the iOS native project. `cap add ios` needs macOS, and nobody on this
  project has a Mac, so it is created **in CI**: the `ios-bootstrap` workflow runs it on a
  GitHub-hosted macOS runner and hands back the generated project to commit
  ([#531](https://github.com/zelytra/Librarius/issues/531), § 10). Nobody has run it yet.
- **The status bar's own colours.** The app holds the system bars off its content (§ 6), but
  their icons still follow the device's dark mode rather than the palette the reader chose —
  [#533](https://github.com/zelytra/Librarius/issues/533).
- **Any plugin an issue has not asked for.** Two are declared, both for sign-in:
  `@capacitor/browser` and `@capacitor/app` (§ 5). The camera comes with
  [#68](https://github.com/zelytra/Librarius/issues/68) — today the scanner reads the camera
  through `getUserMedia`, which the WebView grants from the manifest permission — and push
  with [#69](https://github.com/zelytra/Librarius/issues/69).
- **A Play Console account and a published listing.** The procedure is written down —
  `docs/wiki/Mobile-Android-Play-Store.md`, [#530](https://github.com/zelytra/Librarius/issues/530)
  — but the account, the listing, the screenshots and the privacy policy it requires are the
  owner's to create: nothing in this repository can do it.
- **A run on a real device.** Everything the container changes — sign-in through the system
  browser, the safe areas, the API origin — is tested with the plugins faked or in a browser.
  Nothing here has been installed on a phone yet; § 5 lists what that run has to confirm.

## 2. How the code is shared with the web app

Two things tie the workspaces together:

```text
apps/mobile/package.json      devDependencies: "@librarius/web": "workspace:*"
apps/mobile/capacitor.config.ts   webDir: '../web/dist'
```

- The **workspace dependency** is what keeps the two installed and versioned together, and
  `pnpm mobile:build` names the order explicitly:
  `@librarius/web build:mobile`, then `@librarius/mobile build` (`cap sync`). Nothing can
  sync a stale bundle.
  The web build runs in Vite's **`mobile` mode** rather than its default one, which is the
  one difference between the bundle the browser gets and the bundle the container gets:
  `apps/web/.env.mobile` names the API and the Keycloak client in full, because neither is
  same-origin from inside the container ([#527](https://github.com/zelytra/Librarius/issues/527),
  [#528](https://github.com/zelytra/Librarius/issues/528)). That is also why `mobile:build`
  spells the chain out instead of letting the workspace dependency run `@librarius/web`'s
  default `build`: the dependency decides the order, not the mode.
- **`webDir` points outside the package**, at the web build output. `cap sync` copies that
  directory into each native project (`android/app/src/main/assets/public`, `ios/App/App/public`).

The dependency is a *build-order* dependency: `apps/mobile` never imports a symbol from
`@librarius/web`, which publishes no entry point. That is the cost of this approach — a
reader may look for an `import` that does not exist, hence this paragraph. What it buys is
that the link is declared rather than conventional: run the build from a clean checkout
and pnpm resolves the order on its own.

Two alternatives were considered and dropped:

- **Copying the bundle into `apps/mobile/www`** as part of a build script: an extra copy to
  keep in sync, and a second directory that can go stale. `webDir` reaches the real output
  with no copy at all.
- **A `packages/app` library consumed by a mobile-specific Vite build**: the only reason to
  split would be a mobile-specific entry point, and there is none — the whole point of the
  milestone is that the screens are written once.

### Adding a plugin, later

A Capacitor plugin has two halves. The JavaScript half is imported by application code,
which lives in `apps/web`; the native half is registered by `cap sync`, which reads the
`dependencies` of the package holding `capacitor.config.ts`. So a plugin (`@capacitor/camera`,
`@capacitor/push-notifications`, …) has to be declared in **both** `apps/web/package.json`
and `apps/mobile/package.json`, on the same version. Declaring it only in `apps/web` builds
fine and does nothing on the device.

`@capacitor/core` follows the same rule: `apps/web` imports it (`Capacitor.isNativePlatform()`
in `src/auth/oidc.ts`), `apps/mobile` declares it because the platform packages need it.

## 3. Commands

| Command | Effect |
|---|---|
| `pnpm mobile:build` | Builds `@librarius/web` **in `mobile` mode**, then `cap sync` |
| `pnpm --filter @librarius/mobile typecheck` | Type-checks `capacitor.config.ts` |
| `pnpm --filter @librarius/mobile add:android` | `cap add android` — do **not** run this again; `android/` already exists and `cap add` overwrites hand-edited files (§ 7) |
| `pnpm --filter @librarius/mobile open:android` | Opens the native project in Android Studio — run `pnpm mobile:build` first, or the project opens without a web bundle to serve |
| `pnpm --filter @librarius/mobile doctor` | Prints the versions Capacitor sees |

With no native platform installed, `cap sync` reports `copy web` / `update web` and exits 0.
It still **fails when `apps/web/dist` is missing**, which is what the `mobile` CI job leans
on: it is the check that the two workspaces are still wired together.

**Building the APK itself needs the Android SDK**, not installed on every machine (§ 4):

```bash
pnpm mobile:build                       # web build + cap sync, from the repository root
cd apps/mobile/android && ./gradlew assembleDebug   # app/build/outputs/apk/debug/app-debug.apk
```

No Windows machine in this project has the Android SDK — see § 7 for where this is actually
exercised.

## 4. Prerequisites for the native projects

Nothing beyond Node 24 and pnpm is needed to work on the workspace itself — `capacitor.config.ts`,
`package.json`, the JS/TS side of things. **Building the Android project needs more**, whether
that build happens locally or in CI:

| Platform | Requirements | Where they come from in CI |
|---|---|---|
| Android | Android Studio (for local development only), the Android SDK (API 24+), a JDK 21 — the one already used by `apps/api` | `ubuntu-latest` ships a recent SDK (platforms and build-tools past API 36) out of the box; `actions/setup-java` installs Temurin 21. Nothing to configure. |
| iOS | macOS and Xcode — Capacitor 8 uses Swift Package Manager, so no CocoaPods — plus a paid Apple Developer Program membership to reach a device or TestFlight | `macos-latest`, which carries Xcode: `ios-bootstrap.yml` creates the project, `ios-release.yml` builds and uploads it (§ 10). Free on this public repository. |

No Windows machine used on this project has the Android SDK, and none is expected to: the
Android build is verified on the GitHub-hosted runner, not locally — § 7.

**Version note.** The workspace runs **Capacitor 8** since
[#524](https://github.com/zelytra/Librarius/issues/524). It was pinned to 7.x while the
repository built on Node 20, and stayed there afterwards as an untried bump; what forced the
move is Google Play, which requires **API level 36** of every new app and every update since
31 August 2026. API 36 needs AGP 8.13, and AGP 8.13 is what the Capacitor 8 scaffold brings:

| | Capacitor 7 | Capacitor 8 |
|---|---|---|
| `minSdkVersion` | 23 (Android 6.0) | **24** (Android 7.0) |
| `compileSdkVersion` / `targetSdkVersion` | 35 | **36** |
| Android Gradle plugin | 8.7.2 | **8.13.0** |
| Gradle wrapper | 8.11.1 | **8.14.3** |
| `com.google.gms:google-services` | 4.4.2 | 4.4.4 |

Two consequences to know:

- **Android 6.0 is dropped** by the `minSdkVersion` floor — around 0.2 % of devices still in
  use, and none that would run this app well.
- **`android.adjustMarginsForEdgeToEdge` no longer exists.** Capacitor 8 replaces it with the
  built-in `SystemBars` plugin, whose `insetsHandling` defaults to `css`: the container stays
  edge-to-edge and the web app reads `env(safe-area-inset-*)` itself — § 6 and
  [#529](https://github.com/zelytra/Librarius/issues/529).

The upgrade was mechanical because `android/` is the stock template plus a handful of hand
edits (§ 7): eight files differ between the 7 and 8 scaffolds, and only `app/build.gradle` and
`AndroidManifest.xml` of them carry edits of ours to re-apply.

## 5. Authentication in the container

Implemented by [#528](https://github.com/zelytra/Librarius/issues/528). It is the one part of
this workspace that **no test and no CI job can prove**: the pieces below are unit-tested with
the plugins faked, and only a run on a device shows that the OS routes the callback back.

### Why the browser flow cannot be reused as it is

- **The origin is not an address.** The WebView serves the bundle from `https://localhost`
  (Android) or `capacitor://localhost` (iOS) — the same two values for every installation of
  every Capacitor app — so neither can be a redirect target.
- **The sign-in page must not run in the WebView.** RFC 8252 (OAuth 2.0 for Native Apps)
  requires the system browser: an embedded WebView gives the app access to the credentials
  typed into it, and its cookie jar is private to the app, so there is no single sign-on with
  the browser and every launch would ask for the password again.
- **The callback comes back out of band**, through a custom scheme the OS routes to the app,
  not through a page navigation the WebView can follow.

### How it works now

| Piece | Where |
|---|---|
| `fr.zelytra.librarius://auth` as redirect and post-logout URI | `apps/web/src/auth/nativeAuth.ts` (`NATIVE_REDIRECT_URI`), used by `auth/oidc.ts` when `Capacitor.isNativePlatform()` |
| The authorization page opened in a Custom Tab / `ASWebAuthenticationSession` | `systemBrowserNavigator`, the `INavigator` given to `new UserManager(settings, …)` in place of the redirect navigator |
| The callback link turned back into a signed-in session | `routeAuthCallbacks`, registered once in `main.tsx`: it listens for `appUrlOpen`, closes the browser and calls `signinCallback(url)` — or `signoutCallback(url)` for the sign-out leg, told apart by the presence of `code`/`error` |
| The scheme registered natively | the second `<intent-filter>` in `AndroidManifest.xml`, on `@string/custom_url_scheme`; `CFBundleURLTypes` on the iOS side ([#531](https://github.com/zelytra/Librarius/issues/531)) |
| The Keycloak client | `librarius-mobile`, public, PKCE `S256`, direct access grants off, in `infra/keycloak/realm-librarius.json` **and** the realm embedded in `infra/helm/librarius/templates/keycloak.yaml` — **and** created on the live realm by the `keycloak-setup` Job, because a realm is imported once and staging's was imported long before this client existed |
| Which client the app asks for | `VITE_OIDC_CLIENT_ID=librarius-mobile` in `apps/web/.env.mobile` |

Two details that are easy to get wrong and expensive to debug:

- **`webOrigins` has to list the two container origins explicitly.** `"+"` derives the allowed
  origins from the redirect URIs, and a custom scheme derives nothing: without
  `https://localhost` and `capacitor://localhost` the token exchange fails on CORS *after* a
  sign-in that looked successful.
- **`signinRedirect()` ignores whatever the navigator returns** (`_signinStart` awaits
  `handle.navigate(…)` and drops the result), which is why the callback cannot be handed back
  through the navigator and `routeAuthCallbacks` exists instead.

### What a device run has to confirm

1. The sign-in button opens the **system browser**, not a page inside the app.
2. Coming back lands on the app signed in, with the library loaded — which also proves the
   CORS origins of § 6.
3. Closing the browser without signing in leaves the app usable.
4. Signing out ends the Keycloak session: signing in again asks for the password.
5. Reopening the app days later is still signed in (the offline token), with no browser.

## 6. What else the container changes

Two more things that a native build will hit, neither of them auth:

- **The API is no longer same-origin** — handled since
  [#527](https://github.com/zelytra/Librarius/issues/527). The generated client calls relative
  URLs (`/api/library`, orval `baseUrl: ''`), which the browser resolves against the page
  origin; inside the container that origin is the bundle itself, so every call looked for the
  API in the packaged assets. `apps/web/src/shared/apiBase.ts` now prefixes
  `VITE_API_BASE_URL` to every API path, in the two places that reach the network
  (`shared/apiClient.ts` for the generated hooks, `shared/authorisedGet.ts` for the avatar
  and the export). The variable is empty on a web build, so the browser and the Vite dev
  proxy are byte-for-byte unchanged; `apps/web/.env.mobile` sets it for the native build, and
  the API's `CORS_ORIGINS` accepts `https://localhost` and `capacitor://localhost`
  (`application.properties` default and `infra/helm/librarius/templates/api.yaml`, locked by
  `CorsTest`).
- **Safe areas** — handled since [#529](https://github.com/zelytra/Librarius/issues/529). An
  app that targets API 35 or later is edge-to-edge: the WebView fills the window, status bar
  and gesture bar included. Capacitor 8 has no `adjustMarginsForEdgeToEdge` to hand that back
  to the native side; its `SystemBars` plugin fills `env(safe-area-inset-*)` in instead
  (`insetsHandling: "css"`, its default), and `capacitor.config.ts` adds
  `initialViewportFitValueHint: "cover"` so the first frame is not laid out and then shifted.
  The shell reads the insets: `AppShell.module.css` holds the top and the two sides off the
  frame, `BottomNav.module.css` reserves the gesture bar under the bar — every one with a
  `0px` fallback, so a browser lays the app out exactly as before (`app/safeAreas.test.ts`).
  **The status bar's own icons are not handled**: they follow the device's dark mode, not the
  palette the reader chose — [#533](https://github.com/zelytra/Librarius/issues/533).

## 7. Continuous integration

Three workflows touch this workspace now:

- **`sync`** (`.github/workflows/mobile.yml`) — install, `typecheck`, then `pnpm mobile:build`.
  Needs no SDK and no emulator, checks nothing beyond the web ↔ native wiring, and is what
  ran here before [#70](https://github.com/zelytra/Librarius/issues/70).
- **`android-debug`** (same file) — the same build, one step further:
  `cd apps/mobile/android && ./gradlew assembleDebug`, the result uploaded as the
  `librarius-debug-apk` workflow artifact (7-day retention). Runs on every push to `main` and
  every pull request touching the same paths as `sync`, so a reviewer can pull the APK from
  the run and sideload it without owning an Android SDK.
- **`ios-bootstrap.yml`** and **`ios-release.yml`** — the iOS pair, on `macos-latest`; § 10.
- **`mobile-release.yml`** — a separate, tag-triggered workflow (`push: tags: v*`, the same
  pattern `release.yml` uses), which builds a **signed** release APK once the keystore
  secrets exist. § 8 is the procedure to create them; until it has been followed, the
  `build` job explains what is missing in a `::warning::` annotation and exits green rather
  than red — nothing about the build is broken, only a manual step nobody has done yet.

None of the three installs the Android SDK by hand: `ubuntu-latest` already carries the
platforms and build-tools this project's `compileSdk`/`targetSdk` (36, `variables.gradle`)
need — `actions/setup-java` adds the matching Temurin 21, and `gradle/actions/setup-gradle`
caches `~/.gradle` and validates the committed wrapper jar's checksum. This matters because
**no machine used on this project has the Android SDK either**: the pipeline was written and
reviewed on Windows without ever running Gradle locally. Treat the first run on the pull
request that introduces it as the real verification, not this document.

Adding `android/` does **not** change the web image build: `apps/web/Dockerfile` copies only
`apps/web/package.json` into its context, and `pnpm install --frozen-lockfile` accepts a
workspace member that is absent from the context — verified by building the image, the same
check the workspace's original bootstrap relied on.

### What is committed, and what is not

`apps/mobile/android/` is **committed**, not regenerated by CI on every run. The
alternative — running `cap add android` fresh in CI, never versioning the directory at
all — was considered and rejected:

- Capacitor's native projects are meant to be hand-edited, not treated as a build output.
  The signing config in `app/build.gradle` (§ 8) and the future auth intent-filter in
  `AndroidManifest.xml` (§ 5) both live in files `cap add` writes once and never touches
  again; regenerating from scratch on every build would discard both every time, which would
  demand a second layer of patch scripts just to reapply them — the over-engineering
  `.claude/docs/CONVENTIONS.md` argues against when a plain committed file already does the
  job.
- The ordinary native workflow — opening the project in Android Studio, setting a
  breakpoint, running the instrumented tests — needs the files to exist on disk before any
  build runs, not conjured by a CI step nobody runs locally.

The cost of this choice falls due **the day Capacitor's own version moves**, not before: a
`@capacitor/android` bump can change what a fresh `cap add` would scaffold today (Gradle
wrapper version, AGP version, target/compile SDK, template boilerplate), and a committed
`android/` does not pick any of that up by itself. `cap sync` does **not** re-scaffold these
files — it only refreshes the web assets and the plugin list. Whoever bumps
`@capacitor/android` has to re-run `cap add android` deliberately (which will prompt before
overwriting) and manually re-apply the signing config and any other hand edit — the same
"tried deliberately, not inherited silently" discipline § 4 already asks of the 7 → 8 CLI
bump itself.

Not everything under `android/` is committed, though. `cap sync` / `cap update` rewrite some
files on every single run, so tracking them would either drift the moment someone forgets to
sync before committing, or churn on every CI run for nothing — `android/.gitignore` excludes,
on top of the stock Capacitor template's own list:

- `app/capacitor.build.gradle` and `capacitor.settings.gradle` — both carry Capacitor's own
  "DO NOT EDIT, GENERATED EACH TIME `capacitor update` IS RUN" banner.
  `capacitor.settings.gradle` additionally pins the *exact* pnpm virtual-store path of
  `@capacitor/android` (`node_modules/.pnpm/@capacitor+android@7.6.8_@capacitor+core@7.6.8/…`
  today), which is resolution-specific and can change without `@capacitor/android`'s own
  version changing at all.
- `*.jks` / `*.keystore` — commented out, i.e. *not* actually ignored, in Capacitor's stock
  template. Uncommented here: the release keystore must never be committed (§ 8), and this
  is a local backstop alongside `secrets.yml`'s gitleaks scan.

Every job above runs `pnpm mobile:build` (`cap sync`) before touching Gradle, so these files
are always freshly regenerated in CI regardless of what git holds — ignoring them costs
nothing there. It only matters for whoever opens `android/` directly: run `pnpm mobile:build`
first, or Gradle's sync fails on missing files, the same way it already does today on the
equally-ignored `assets/public` and `capacitor.config.json`.

### A Windows-specific trap: the Gradle wrapper's executable bit

`gradlew` was generated and committed from a Windows checkout, where `core.filemode` is
`false` and NTFS has no executable bit to preserve. Staged the ordinary way, `gradlew` would
land in git as `100644`, and `./gradlew` would then fail with *Permission denied* on the
Linux runner — long after anyone could tell why from the diff. It is committed as `100755`
(`git update-index --chmod=+x apps/mobile/android/gradlew`); if `gradlew` is ever
regenerated from a Windows checkout (a Capacitor bump, above), reapply this before pushing.
`git ls-files -s apps/mobile/android/gradlew` should read `100755`, never `100644`.

## 8. Release signing — creating the keystore secrets

Nobody has created a release keystore for Librarius yet, and this document does not invent
one: a keystore is the one credential that, if lost, permanently blocks updating the app
under its existing identity on every device that already installed it. Generating it is a
decision for whoever owns the Play Console account, not for CI or an agent working through
an issue.

`mobile-release.yml` reads four repository secrets that do not exist today — GitHub UI path:
Settings → Secrets and variables → Actions → New repository secret, on
`github.com/zelytra/Librarius`:

| Secret | Contents |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | The whole keystore file, base64-encoded |
| `ANDROID_KEYSTORE_PASSWORD` | The keystore's store password |
| `ANDROID_KEY_ALIAS` | The alias of the signing key inside that keystore |
| `ANDROID_KEY_PASSWORD` | That key's own password (`keytool` accepts the same value as the store password below, but prompts for both separately) |

They are read only by `mobile-release.yml`, decoded into `$RUNNER_TEMP` — never into the
git checkout — and handed to Gradle as `-P` properties consumed by the `signingConfigs.release`
block in `apps/mobile/android/app/build.gradle`, which links back to this section. No step
prints any of the four, and GitHub additionally masks a secret's literal value out of every
log the moment a workflow references it.

### Procedure — for the project owner; not something CI or an agent should run

1. **Generate the keystore once**, on a machine whose backups you trust — it is not
   recoverable if lost, and losing it means every future release needs a new application ID:

   ```bash
   keytool -genkeypair -v -keystore librarius-release.jks -alias librarius \
     -keyalg RSA -keysize 2048 -validity 10000
   ```

   `keytool` prompts for the store password, the key password (press Enter to reuse the
   store password) and a distinguished name — the name does not need to be accurate, the
   passwords need to be kept.
2. **Back up `librarius-release.jks` outside this repository** — a password manager's file
   storage or equivalent. `android/.gitignore` now refuses `*.jks` / `*.keystore` as a
   backstop (§ 7), not as the actual safeguard: the real one is never putting it there.
3. **Base64-encode it** for the secret value, e.g. `base64 librarius-release.jks >
   librarius-release.jks.b64` (macOS or Linux `base64`; the line-wrapping either produces
   does not matter, `base64 -d` on the decoding side ignores it). On Windows, do this from
   WSL or Git Bash rather than `certutil`, which wraps the output in PEM headers that would
   have to be stripped by hand.
4. **Create the four secrets** listed above. Paste the base64 text into
   `ANDROID_KEYSTORE_BASE64` — not the raw keystore file.

Once all four exist, the next `vX.Y.Z` tag
(`.claude/docs/CONVENTIONS.md` § "When a tag is cut") is what actually exercises this path
for the first time: nothing before that point — this document included — has compiled it.

## 9. Icon, splash screen and store artwork

The launcher icon and the launch screen are **generated**, not drawn by hand. Five SVG
sources live in `apps/mobile/assets/`, all of them the web app's open-book mark
(`apps/web/public/favicon.svg`) on the application's own background token:

| Source | Becomes |
|---|---|
| `icon-only.svg` | `mipmap-*/ic_launcher.png` and `ic_launcher_round.png` — the icon of Android 7 and 8.0, which know nothing of adaptive icons |
| `icon-foreground.svg` | `mipmap-*/ic_launcher_foreground.png`, the adaptive icon's mark |
| `icon-background.svg` | `mipmap-*/ic_launcher_background.png`, its flat background |
| `splash.svg`, `splash-dark.svg` | `drawable*/splash.png` at every density, orientation and night variant |

```bash
pnpm --filter @librarius/mobile assets:generate   # the native resources
pnpm --filter @librarius/mobile store:assets      # the Play Console's two images
```

Three things worth knowing before touching any of it:

- **The foreground has to stay inside the safe zone.** A launcher masks an adaptive icon with
  its own shape, and only the central 66 % always survives. `icon-foreground.svg` is cropped
  to the mark plus a tenth of its size, and the generated `mipmap-anydpi-v26/ic_launcher.xml`
  insets it by a further 16.7 %.
- **The background must not be inset.** `@capacitor/assets` writes both layers inset, which
  leaves the four corners transparent and makes a round mask cut a hole in the icon;
  `scripts/finish-android-icons.mjs` rewrites those two files right after the generator and
  removes the template leftovers nothing references any more. That is why `assets:generate`
  is two commands rather than one.
- **The generator reformats `AndroidManifest.xml`** (it parses and rewrites it). It keeps the
  content, comments included; the diff is whitespace. Nothing to undo.

`apps/mobile/store/` holds what the Play Console asks for and the native project does not
use: `icon-512.png` (512 × 512, no alpha — Play refuses one) and `feature-graphic.png`
(1024 × 500), both rendered from the SVG beside them. **Screenshots are not in here**: Play
wants between two and eight real ones per form factor, and only a run on a device or a signed
-in browser at phone width can produce them — `docs/wiki/Mobile-Android-Play-Store.md` says what to
shoot.

## 10. iOS, with no Mac anywhere

The owner has an iPhone and no Mac, and every Apple tool that matters — `xcodebuild`, the
signing machinery, the uploader — is macOS-only. The way through is to rent the Mac by the
minute and let Apple issue the signing material itself. Two workflows, neither of which has
run yet ([#531](https://github.com/zelytra/Librarius/issues/531)):

| Workflow | When | What it does |
|---|---|---|
| `ios-bootstrap.yml` | By hand, once | `cap add ios` on `macos-latest`, then `scripts/patch-ios-project.sh`, then hands the project back as an artifact (or pushes it to a branch). It refuses to run while `apps/mobile/ios` exists. |
| `ios-release.yml` | Every `v*` tag | Web build, `cap sync`, `xcodebuild archive`, `xcodebuild -exportArchive` with `destination: upload` — straight into TestFlight. Skips with an annotation while the project or the secrets are missing. |

What makes it work without a Mac is **cloud-managed signing**: `xcodebuild` is given
`-allowProvisioningUpdates` and an App Store Connect **API key** (Admin role — the lesser
roles are refused), and asks Apple for the distribution certificate and the provisioning
profile during the build. No `.p12`, no `fastlane match` repository, nothing to renew.

Three facts about the Capacitor 8 iOS scaffold that the workflows depend on:

- it is a **Swift Package Manager** project (`ios-spm-template`), so there is no `Podfile`,
  no `App.xcworkspace`, and `xcodebuild -project App.xcodeproj` is the right invocation;
- the version is read from the **build settings**, not from `Info.plist`
  (`CFBundleShortVersionString` is `$(MARKETING_VERSION)`), so the tag's version is passed to
  `xcodebuild` rather than written into the plist;
- the hand edits — `CFBundleURLTypes` for `fr.zelytra.librarius://auth` and the French
  `NSCameraUsageDescription` — are applied by `scripts/patch-ios-project.sh`, which is
  idempotent and has to be re-run after any `cap add ios`.

The procedure, with costs and lead times, is `docs/wiki/Mobile-iOS-Pipeline.md`. The device
checks that none of this can prove — sign-in, the scanner, the safe areas — stay on
[#71](https://github.com/zelytra/Librarius/issues/71).
