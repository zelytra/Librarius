# Native mobile shell — `apps/mobile`

> Bootstrapped on 2026-07-28 by [#67](https://github.com/zelytra/Librarius/issues/67).
> Describes what the workspace **is today**, and what the rest of the v0.6 milestone
> ([#68](https://github.com/zelytra/Librarius/issues/68) to
> [#71](https://github.com/zelytra/Librarius/issues/71)) still has to do.

## 1. What this workspace is

A **Capacitor 7 container**. Beyond `capacitor.config.ts`, `tsconfig.json` and
`package.json`, it now also holds `android/` — the native Android project, generated by
`cap add android` and committed since [#70](https://github.com/zelytra/Librarius/issues/70)
(§ 7 explains why committed rather than regenerated). None of it is application code in the
usual sense: **no React code, no screen, no style** anywhere in this workspace. The
application that runs inside the container is `apps/web`, exactly the bundle the browser
gets — `android/` is packaging around that bundle, not a second copy of the app.

What is deliberately **not** here yet:

- `apps/mobile/ios/` — the iOS native project, needing Xcode and a paid Apple developer
  account. Comes with [#71](https://github.com/zelytra/Librarius/issues/71).
- **Librarius' own icon and splash screen.** `cap add` always writes Capacitor's stock
  placeholder artwork at every density (`android/app/src/main/res/mipmap-*/ic_launcher*.png`,
  `drawable*/splash.png`); nobody has replaced them yet, so a debug APK built today shows
  the generic Capacitor mark, not the Librarius logo. Unclaimed work, not blocked on
  anything.
- Status bar colour and edge-to-edge / safe-area handling: real settings of the native
  project that now exists, still unset. See § 6.
- Any plugin. A plugin that no issue asks for is dead weight the next agent has to
  explain; the camera comes with [#68](https://github.com/zelytra/Librarius/issues/68),
  push with [#69](https://github.com/zelytra/Librarius/issues/69).

## 2. How the code is shared with the web app

Two things tie the workspaces together:

```text
apps/mobile/package.json      devDependencies: "@librarius/web": "workspace:*"
apps/mobile/capacitor.config.ts   webDir: '../web/dist'
```

- The **workspace dependency** is what makes the ordering explicit:
  `pnpm --filter "@librarius/mobile..." build` (aliased to `pnpm mobile:build`) runs
  `@librarius/web build` first, then `cap sync`. Nothing can sync a stale bundle.
- **`webDir` points outside the package**, at the web build output. `cap sync` copies that
  directory into each native project (`android/app/src/main/assets/public`, `ios/App/App/public`).

The dependency is a *build-order* dependency: `apps/mobile` never imports a symbol from
`@librarius/web`, which publishes no entry point. That is the cost of this approach — a
reader may look for an `import` that does not exist, hence this paragraph. What it buys is
that the link is declared rather than conventional: run the build from a clean checkout
and pnpm resolves the order on its own.

Two alternatives were considered and dropped:

- **Copying the bundle into `apps/mobile/www`** as part of a build script: an extra copy to
  keep in sync, and a second directory that can go stale. `webDir` reaches the real output
  with no copy at all.
- **A `packages/app` library consumed by a mobile-specific Vite build**: the only reason to
  split would be a mobile-specific entry point, and there is none — the whole point of the
  milestone is that the screens are written once.

### Adding a plugin, later

A Capacitor plugin has two halves. The JavaScript half is imported by application code,
which lives in `apps/web`; the native half is registered by `cap sync`, which reads the
`dependencies` of the package holding `capacitor.config.ts`. So a plugin (`@capacitor/camera`,
`@capacitor/push-notifications`, …) has to be declared in **both** `apps/web/package.json`
and `apps/mobile/package.json`, on the same version. Declaring it only in `apps/web` builds
fine and does nothing on the device.

`@capacitor/core` follows the same rule: `apps/web` imports it (`Capacitor.isNativePlatform()`
in `src/auth/oidc.ts`), `apps/mobile` declares it because the platform packages need it.

## 3. Commands

| Command | Effect |
|---|---|
| `pnpm mobile:build` | Builds `@librarius/web`, then `cap sync` |
| `pnpm --filter @librarius/mobile typecheck` | Type-checks `capacitor.config.ts` |
| `pnpm --filter @librarius/mobile add:android` | `cap add android` — do **not** run this again; `android/` already exists and `cap add` overwrites hand-edited files (§ 7) |
| `pnpm --filter @librarius/mobile open:android` | Opens the native project in Android Studio — run `pnpm mobile:build` first, or the project opens without a web bundle to serve |
| `pnpm --filter @librarius/mobile doctor` | Prints the versions Capacitor sees |

With no native platform installed, `cap sync` reports `copy web` / `update web` and exits 0.
It still **fails when `apps/web/dist` is missing**, which is what the `mobile` CI job leans
on: it is the check that the two workspaces are still wired together.

**Building the APK itself needs the Android SDK**, not installed on every machine (§ 4):

```bash
pnpm mobile:build                       # web build + cap sync, from the repository root
cd apps/mobile/android && ./gradlew assembleDebug   # app/build/outputs/apk/debug/app-debug.apk
```

No Windows machine in this project has the Android SDK — see § 7 for where this is actually
exercised.

## 4. Prerequisites for the native projects

Nothing beyond Node 24 and pnpm is needed to work on the workspace itself — `capacitor.config.ts`,
`package.json`, the JS/TS side of things. **Building the Android project needs more**, whether
that build happens locally or in CI:

| Platform | Requirements | Where they come from in CI |
|---|---|---|
| Android | Android Studio (for local development only), the Android SDK (API 23+), a JDK 21 — the one already used by `apps/api` | `ubuntu-latest` ships a recent SDK (platforms and build-tools well past API 35) out of the box; `actions/setup-java` installs Temurin 21. Nothing to configure. |
| iOS | macOS, Xcode, CocoaPods, a paid Apple developer account for a device or TestFlight | Not built in CI yet — [#71](https://github.com/zelytra/Librarius/issues/71). |

No Windows machine used on this project has the Android SDK, and none is expected to: the
Android build is verified on the GitHub-hosted runner, not locally — § 7.

**Version note.** Capacitor was pinned to **7.x** because `@capacitor/cli` 8 declares
`node >= 22` while the repository still built on Node 20. **That constraint is gone**:
`.nvmrc` moved to **24** with the toolchain upgrade
([#133](https://github.com/zelytra/Librarius/issues/133)), Node 20 having reached end of
life in April 2026.

So 8.x is now merely **untried**, not blocked. The pin stays until someone moves it
deliberately and runs `pnpm mobile:build` against it — a major bump nobody has exercised is
not something to inherit silently while [#68](https://github.com/zelytra/Librarius/issues/68)
to [#71](https://github.com/zelytra/Librarius/issues/71) are still unwritten. Whoever picks
one of them up should try 8 first, rather than building on 7 and migrating afterwards.

## 5. Authentication — what does not work yet

**This is the open point of the bootstrap.** The redirect URI is branched and tested; the
flow around it is not implemented, and it will not work by accident.

### What the web app does today

`apps/web/src/auth/oidc.ts` configures Authorization Code + PKCE through
`react-oidc-context`: `redirect_uri` is `window.location.origin`, the session is stored in
`localStorage`, and `signinRedirect()` navigates the page to Keycloak.

### What breaks inside the container

- **The origin is not an address.** The WebView serves the bundle from `https://localhost`
  (Android) or `capacitor://localhost` (iOS) — the same two values for every installation
  of every Capacitor app. Keycloak cannot use either as a redirect target.
- **The sign-in page must not run in the WebView.** RFC 8252 (OAuth 2.0 for Native Apps)
  requires the system browser: an embedded WebView gives the app access to the credentials
  typed into it, and its cookie jar is separate, so there is no single sign-on with the
  browser and every launch asks for the password again.
- **The callback comes back out of band**, through a custom scheme the OS routes to the
  app, not through a page navigation the WebView can follow.

### What is already in place

`redirect_uri` and `post_logout_redirect_uri` become `fr.zelytra.librarius://auth` when
`Capacitor.isNativePlatform()` is true — a reverse-DNS scheme mirroring the Capacitor
`appId`, rather than the `librarius://` of the issue, because any application installed on
the device can claim a short scheme. Both branches are locked by
`apps/web/src/auth/oidc.test.ts`. The web behaviour is byte-for-byte what it was.

### What is still missing, precisely

1. **A Keycloak client for the native app.** The realm declares `librarius-web`, whose
   redirect URIs are the web origins. A public client `librarius-mobile` has to be added to
   `infra/keycloak/realm-librarius.json` **and** to the realm embedded in
   `infra/helm/librarius/templates/keycloak.yaml`, with `redirectUris:
   ["fr.zelytra.librarius://auth"]`, PKCE `S256` required and `directAccessGrantsEnabled`
   off. The app then only needs `VITE_OIDC_CLIENT_ID=librarius-mobile` at build time — the
   variable is already read.
2. **`webOrigins` on that client.** The token exchange is an XHR sent by the WebView, whose
   `Origin` is `https://localhost` or `capacitor://localhost`. `webOrigins: ["+"]` derives
   the allowed origins from the redirect URIs, and a custom scheme derives nothing: both
   origins have to be listed explicitly or the code exchange fails on CORS, after a login
   that looked successful.
3. **Two plugins**: `@capacitor/browser` to open the authorization URL in a Custom Tab /
   `ASWebAuthenticationSession`, and `@capacitor/app` to receive the `appUrlOpen` event
   carrying the callback URL.
4. **A navigator for `oidc-client-ts`.** The seam exists and needs no fork:
   `new UserManager(settings, redirectNavigator)` takes an `INavigator`
   (`prepare(): Promise<IWindow>` / `callback(url)`), and `react-oidc-context` ≥ 3 accepts a
   ready-made instance — `<AuthProvider userManager={…}>`, the `AuthProviderUserManagerProps`
   half of its props union. The native implementation opens the URL with `Browser.open()`,
   waits for `appUrlOpen`, closes the browser and hands the URL to `signinCallback(url)`,
   which finishes PKCE against the verifier kept in storage.
5. **The scheme registered natively**: an `<intent-filter>` with
   `android:scheme="fr.zelytra.librarius"` in `AndroidManifest.xml`, and the matching
   `CFBundleURLTypes` entry in `Info.plist`. `AndroidManifest.xml` exists now
   ([#70](https://github.com/zelytra/Librarius/issues/70)) and deliberately carries no such
   intent-filter yet — auth stayed out of #70's scope on purpose (§ 7), it is not blocked by
   anything technical any more. `Info.plist` still does not exist —
   [#71](https://github.com/zelytra/Librarius/issues/71).

Point 4 is the only real code, and it is perhaps thirty lines. It is deliberately not
written here: nothing in this repository can run it — no native project, no device, no
emulator — and an untested authentication flow that *looks* implemented is worse than an
absent one.

## 6. What else the container changes

Two more things that a native build will hit, neither of them auth:

- **The API is no longer same-origin.** The generated client calls relative URLs
  (`/api/library`, orval `baseUrl: ''`), which the browser resolves against the page origin.
  Inside the container that origin is the bundle itself, so every call would look for the API
  in the packaged assets. The native build needs an absolute base URL — a `VITE_API_BASE_URL`
  read by `shared/apiClient.ts` is enough, empty by default so the web is untouched — and the
  API needs its `CORS_ORIGINS` (`apps/api/src/main/resources/application.properties`, wired
  through `infra/helm/librarius/templates/api.yaml`) to accept `https://localhost` and
  `capacitor://localhost`.
- **Safe areas and the status bar.** `index.html` already carries `viewport-fit=cover`, but
  no rule reads `env(safe-area-inset-*)`, so the bottom navigation would sit under the
  gesture bar. The fix belongs with the native project: Capacitor 7 can handle Android 15
  edge-to-edge itself (`android.adjustMarginsForEdgeToEdge`), and that decision determines
  whether the insets reach the CSS at all. The native project #70 adds does not set this
  either way — still open, and now unblocked rather than guessed at here.

## 7. Continuous integration

Three workflows touch this workspace now:

- **`sync`** (`.github/workflows/mobile.yml`) — install, `typecheck`, then `pnpm mobile:build`.
  Needs no SDK and no emulator, checks nothing beyond the web ↔ native wiring, and is what
  ran here before [#70](https://github.com/zelytra/Librarius/issues/70).
- **`android-debug`** (same file) — the same build, one step further:
  `cd apps/mobile/android && ./gradlew assembleDebug`, the result uploaded as the
  `librarius-debug-apk` workflow artifact (7-day retention). Runs on every push to `main` and
  every pull request touching the same paths as `sync`, so a reviewer can pull the APK from
  the run and sideload it without owning an Android SDK.
- **`mobile-release.yml`** — a separate, tag-triggered workflow (`push: tags: v*`, the same
  pattern `release.yml` uses), which builds a **signed** release APK once the keystore
  secrets exist. § 8 is the procedure to create them; until it has been followed, the
  `build` job explains what is missing in a `::warning::` annotation and exits green rather
  than red — nothing about the build is broken, only a manual step nobody has done yet.

None of the three installs the Android SDK by hand: `ubuntu-latest` already carries the
platforms and build-tools this project's `compileSdk`/`targetSdk` (35, `variables.gradle`)
need — `actions/setup-java` adds the matching Temurin 21, and `gradle/actions/setup-gradle`
caches `~/.gradle` and validates the committed wrapper jar's checksum. This matters because
**no machine used on this project has the Android SDK either**: the pipeline was written and
reviewed on Windows without ever running Gradle locally. Treat the first run on the pull
request that introduces it as the real verification, not this document.

Adding `android/` does **not** change the web image build: `apps/web/Dockerfile` copies only
`apps/web/package.json` into its context, and `pnpm install --frozen-lockfile` accepts a
workspace member that is absent from the context — verified by building the image, the same
check the workspace's original bootstrap relied on.

### What is committed, and what is not

`apps/mobile/android/` is **committed**, not regenerated by CI on every run. The
alternative — running `cap add android` fresh in CI, never versioning the directory at
all — was considered and rejected:

- Capacitor's native projects are meant to be hand-edited, not treated as a build output.
  The signing config in `app/build.gradle` (§ 8) and the future auth intent-filter in
  `AndroidManifest.xml` (§ 5) both live in files `cap add` writes once and never touches
  again; regenerating from scratch on every build would discard both every time, which would
  demand a second layer of patch scripts just to reapply them — the over-engineering
  `.claude/docs/CONVENTIONS.md` argues against when a plain committed file already does the
  job.
- The ordinary native workflow — opening the project in Android Studio, setting a
  breakpoint, running the instrumented tests — needs the files to exist on disk before any
  build runs, not conjured by a CI step nobody runs locally.

The cost of this choice falls due **the day Capacitor's own version moves**, not before: a
`@capacitor/android` bump can change what a fresh `cap add` would scaffold today (Gradle
wrapper version, AGP version, target/compile SDK, template boilerplate), and a committed
`android/` does not pick any of that up by itself. `cap sync` does **not** re-scaffold these
files — it only refreshes the web assets and the plugin list. Whoever bumps
`@capacitor/android` has to re-run `cap add android` deliberately (which will prompt before
overwriting) and manually re-apply the signing config and any other hand edit — the same
"tried deliberately, not inherited silently" discipline § 4 already asks of the 7 → 8 CLI
bump itself.

Not everything under `android/` is committed, though. `cap sync` / `cap update` rewrite some
files on every single run, so tracking them would either drift the moment someone forgets to
sync before committing, or churn on every CI run for nothing — `android/.gitignore` excludes,
on top of the stock Capacitor template's own list:

- `app/capacitor.build.gradle` and `capacitor.settings.gradle` — both carry Capacitor's own
  "DO NOT EDIT, GENERATED EACH TIME `capacitor update` IS RUN" banner.
  `capacitor.settings.gradle` additionally pins the *exact* pnpm virtual-store path of
  `@capacitor/android` (`node_modules/.pnpm/@capacitor+android@7.6.8_@capacitor+core@7.6.8/…`
  today), which is resolution-specific and can change without `@capacitor/android`'s own
  version changing at all.
- `*.jks` / `*.keystore` — commented out, i.e. *not* actually ignored, in Capacitor's stock
  template. Uncommented here: the release keystore must never be committed (§ 8), and this
  is a local backstop alongside `secrets.yml`'s gitleaks scan.

Every job above runs `pnpm mobile:build` (`cap sync`) before touching Gradle, so these files
are always freshly regenerated in CI regardless of what git holds — ignoring them costs
nothing there. It only matters for whoever opens `android/` directly: run `pnpm mobile:build`
first, or Gradle's sync fails on missing files, the same way it already does today on the
equally-ignored `assets/public` and `capacitor.config.json`.

### A Windows-specific trap: the Gradle wrapper's executable bit

`gradlew` was generated and committed from a Windows checkout, where `core.filemode` is
`false` and NTFS has no executable bit to preserve. Staged the ordinary way, `gradlew` would
land in git as `100644`, and `./gradlew` would then fail with *Permission denied* on the
Linux runner — long after anyone could tell why from the diff. It is committed as `100755`
(`git update-index --chmod=+x apps/mobile/android/gradlew`); if `gradlew` is ever
regenerated from a Windows checkout (a Capacitor bump, above), reapply this before pushing.
`git ls-files -s apps/mobile/android/gradlew` should read `100755`, never `100644`.

## 8. Release signing — creating the keystore secrets

Nobody has created a release keystore for Librarius yet, and this document does not invent
one: a keystore is the one credential that, if lost, permanently blocks updating the app
under its existing identity on every device that already installed it. Generating it is a
decision for whoever owns the Play Console account, not for CI or an agent working through
an issue.

`mobile-release.yml` reads four repository secrets that do not exist today — GitHub UI path:
Settings → Secrets and variables → Actions → New repository secret, on
`github.com/zelytra/Librarius`:

| Secret | Contents |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | The whole keystore file, base64-encoded |
| `ANDROID_KEYSTORE_PASSWORD` | The keystore's store password |
| `ANDROID_KEY_ALIAS` | The alias of the signing key inside that keystore |
| `ANDROID_KEY_PASSWORD` | That key's own password (`keytool` accepts the same value as the store password below, but prompts for both separately) |

They are read only by `mobile-release.yml`, decoded into `$RUNNER_TEMP` — never into the
git checkout — and handed to Gradle as `-P` properties consumed by the `signingConfigs.release`
block in `apps/mobile/android/app/build.gradle`, which links back to this section. No step
prints any of the four, and GitHub additionally masks a secret's literal value out of every
log the moment a workflow references it.

### Procedure — for the project owner; not something CI or an agent should run

1. **Generate the keystore once**, on a machine whose backups you trust — it is not
   recoverable if lost, and losing it means every future release needs a new application ID:
   ```bash
   keytool -genkeypair -v -keystore librarius-release.jks -alias librarius \
     -keyalg RSA -keysize 2048 -validity 10000
   ```
   `keytool` prompts for the store password, the key password (press Enter to reuse the
   store password) and a distinguished name — the name does not need to be accurate, the
   passwords need to be kept.
2. **Back up `librarius-release.jks` outside this repository** — a password manager's file
   storage or equivalent. `android/.gitignore` now refuses `*.jks` / `*.keystore` as a
   backstop (§ 7), not as the actual safeguard: the real one is never putting it there.
3. **Base64-encode it** for the secret value, e.g. `base64 librarius-release.jks >
   librarius-release.jks.b64` (macOS or Linux `base64`; the line-wrapping either produces
   does not matter, `base64 -d` on the decoding side ignores it). On Windows, do this from
   WSL or Git Bash rather than `certutil`, which wraps the output in PEM headers that would
   have to be stripped by hand.
4. **Create the four secrets** listed above. Paste the base64 text into
   `ANDROID_KEYSTORE_BASE64` — not the raw keystore file.

Once all four exist, the next `vX.Y.Z` tag
(`.claude/docs/CONVENTIONS.md` § "When a tag is cut") is what actually exercises this path
for the first time: nothing before that point — this document included — has compiled it.
