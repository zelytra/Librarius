# Native mobile shell — `apps/mobile`

> Bootstrapped on 2026-07-28 by [#67](https://github.com/zelytra/Librarius/issues/67).
> Describes what the workspace **is today**, and what the rest of the v0.6 milestone
> ([#68](https://github.com/zelytra/Librarius/issues/68) to
> [#71](https://github.com/zelytra/Librarius/issues/71)) still has to do.

## 1. What this workspace is

A **Capacitor 7 container**, and nothing else. It holds a configuration file, a
`tsconfig.json` and a `package.json`: **no React code, no screen, no style**. The
application that runs inside it is `apps/web`, exactly the bundle the browser gets.

What is deliberately **not** here yet:

- `apps/mobile/android/` and `apps/mobile/ios/` — the native projects, generated by
  `cap add`, which need the Android SDK and Xcode. They come with
  [#70](https://github.com/zelytra/Librarius/issues/70) and
  [#71](https://github.com/zelytra/Librarius/issues/71).
- Icons, splash screen, status bar and safe areas: all of them are settings *of a native
  project*, and none can be checked without one. See § 6.
- Any plugin. A plugin that no issue asks for is dead weight the next agent has to
  explain; the camera comes with [#68](https://github.com/zelytra/Librarius/issues/68),
  push with [#69](https://github.com/zelytra/Librarius/issues/69).

## 2. How the code is shared with the web app

Two things tie the workspaces together:

```text
apps/mobile/package.json      devDependencies: "@librarius/web": "workspace:*"
apps/mobile/capacitor.config.ts   webDir: '../web/dist'
```

- The **workspace dependency** is what makes the ordering explicit:
  `pnpm --filter "@librarius/mobile..." build` (aliased to `pnpm mobile:build`) runs
  `@librarius/web build` first, then `cap sync`. Nothing can sync a stale bundle.
- **`webDir` points outside the package**, at the web build output. `cap sync` copies that
  directory into each native project (`android/app/src/main/assets/public`, `ios/App/App/public`).

The dependency is a *build-order* dependency: `apps/mobile` never imports a symbol from
`@librarius/web`, which publishes no entry point. That is the cost of this approach — a
reader may look for an `import` that does not exist, hence this paragraph. What it buys is
that the link is declared rather than conventional: run the build from a clean checkout
and pnpm resolves the order on its own.

Two alternatives were considered and dropped:

- **Copying the bundle into `apps/mobile/www`** as part of a build script: an extra copy to
  keep in sync, and a second directory that can go stale. `webDir` reaches the real output
  with no copy at all.
- **A `packages/app` library consumed by a mobile-specific Vite build**: the only reason to
  split would be a mobile-specific entry point, and there is none — the whole point of the
  milestone is that the screens are written once.

### Adding a plugin, later

A Capacitor plugin has two halves. The JavaScript half is imported by application code,
which lives in `apps/web`; the native half is registered by `cap sync`, which reads the
`dependencies` of the package holding `capacitor.config.ts`. So a plugin (`@capacitor/camera`,
`@capacitor/push-notifications`, …) has to be declared in **both** `apps/web/package.json`
and `apps/mobile/package.json`, on the same version. Declaring it only in `apps/web` builds
fine and does nothing on the device.

`@capacitor/core` follows the same rule: `apps/web` imports it (`Capacitor.isNativePlatform()`
in `src/auth/oidc.ts`), `apps/mobile` declares it because the platform packages need it.

## 3. Commands

| Command | Effect |
|---|---|
| `pnpm mobile:build` | Builds `@librarius/web`, then `cap sync` |
| `pnpm --filter @librarius/mobile typecheck` | Type-checks `capacitor.config.ts` |
| `pnpm --filter @librarius/mobile add:android` | `cap add android` — creates `apps/mobile/android` |
| `pnpm --filter @librarius/mobile open:android` | Opens the native project in Android Studio |
| `pnpm --filter @librarius/mobile doctor` | Prints the versions Capacitor sees |

With no native platform installed, `cap sync` reports `copy web` / `update web` and exits 0.
It still **fails when `apps/web/dist` is missing**, which is what the `mobile` CI job leans
on: it is the check that the two workspaces are still wired together.

## 4. Prerequisites for the native projects

Nothing beyond Node 24 and pnpm is needed for what is in the repository today. The native
projects need, when [#70](https://github.com/zelytra/Librarius/issues/70) and
[#71](https://github.com/zelytra/Librarius/issues/71) get picked up:

| Platform | Requirements |
|---|---|
| Android | Android Studio, the Android SDK (API 23+), a JDK 21 — the one already used by `apps/api` |
| iOS | macOS, Xcode, CocoaPods, a paid Apple developer account for a device or TestFlight |

**Version note.** Capacitor was pinned to **7.x** because `@capacitor/cli` 8 declares
`node >= 22` while the repository still built on Node 20. **That constraint is gone**:
`.nvmrc` moved to **24** with the toolchain upgrade
([#133](https://github.com/zelytra/Librarius/issues/133)), Node 20 having reached end of
life in April 2026.

So 8.x is now merely **untried**, not blocked. The pin stays until someone moves it
deliberately and runs `pnpm mobile:build` against it — a major bump nobody has exercised is
not something to inherit silently while [#68](https://github.com/zelytra/Librarius/issues/68)
to [#71](https://github.com/zelytra/Librarius/issues/71) are still unwritten. Whoever picks
one of them up should try 8 first, rather than building on 7 and migrating afterwards.

## 5. Authentication — what does not work yet

**This is the open point of the bootstrap.** The redirect URI is branched and tested; the
flow around it is not implemented, and it will not work by accident.

### What the web app does today

`apps/web/src/auth/oidc.ts` configures Authorization Code + PKCE through
`react-oidc-context`: `redirect_uri` is `window.location.origin`, the session is stored in
`localStorage`, and `signinRedirect()` navigates the page to Keycloak.

### What breaks inside the container

- **The origin is not an address.** The WebView serves the bundle from `https://localhost`
  (Android) or `capacitor://localhost` (iOS) — the same two values for every installation
  of every Capacitor app. Keycloak cannot use either as a redirect target.
- **The sign-in page must not run in the WebView.** RFC 8252 (OAuth 2.0 for Native Apps)
  requires the system browser: an embedded WebView gives the app access to the credentials
  typed into it, and its cookie jar is separate, so there is no single sign-on with the
  browser and every launch asks for the password again.
- **The callback comes back out of band**, through a custom scheme the OS routes to the
  app, not through a page navigation the WebView can follow.

### What is already in place

`redirect_uri` and `post_logout_redirect_uri` become `fr.zelytra.librarius://auth` when
`Capacitor.isNativePlatform()` is true — a reverse-DNS scheme mirroring the Capacitor
`appId`, rather than the `librarius://` of the issue, because any application installed on
the device can claim a short scheme. Both branches are locked by
`apps/web/src/auth/oidc.test.ts`. The web behaviour is byte-for-byte what it was.

### What is still missing, precisely

1. **A Keycloak client for the native app.** The realm declares `librarius-web`, whose
   redirect URIs are the web origins. A public client `librarius-mobile` has to be added to
   `infra/keycloak/realm-librarius.json` **and** to the realm embedded in
   `infra/helm/librarius/templates/keycloak.yaml`, with `redirectUris:
   ["fr.zelytra.librarius://auth"]`, PKCE `S256` required and `directAccessGrantsEnabled`
   off. The app then only needs `VITE_OIDC_CLIENT_ID=librarius-mobile` at build time — the
   variable is already read.
2. **`webOrigins` on that client.** The token exchange is an XHR sent by the WebView, whose
   `Origin` is `https://localhost` or `capacitor://localhost`. `webOrigins: ["+"]` derives
   the allowed origins from the redirect URIs, and a custom scheme derives nothing: both
   origins have to be listed explicitly or the code exchange fails on CORS, after a login
   that looked successful.
3. **Two plugins**: `@capacitor/browser` to open the authorization URL in a Custom Tab /
   `ASWebAuthenticationSession`, and `@capacitor/app` to receive the `appUrlOpen` event
   carrying the callback URL.
4. **A navigator for `oidc-client-ts`.** The seam exists and needs no fork:
   `new UserManager(settings, redirectNavigator)` takes an `INavigator`
   (`prepare(): Promise<IWindow>` / `callback(url)`), and `react-oidc-context` ≥ 3 accepts a
   ready-made instance — `<AuthProvider userManager={…}>`, the `AuthProviderUserManagerProps`
   half of its props union. The native implementation opens the URL with `Browser.open()`,
   waits for `appUrlOpen`, closes the browser and hands the URL to `signinCallback(url)`,
   which finishes PKCE against the verifier kept in storage.
5. **The scheme registered natively**: an `<intent-filter>` with
   `android:scheme="fr.zelytra.librarius"` in `AndroidManifest.xml`, and the matching
   `CFBundleURLTypes` entry in `Info.plist`. Neither file exists before `cap add`, which is
   why this cannot be finished before [#70](https://github.com/zelytra/Librarius/issues/70).

Point 4 is the only real code, and it is perhaps thirty lines. It is deliberately not
written here: nothing in this repository can run it — no native project, no device, no
emulator — and an untested authentication flow that *looks* implemented is worse than an
absent one.

## 6. What else the container changes

Two more things that a native build will hit, neither of them auth:

- **The API is no longer same-origin.** The generated client calls relative URLs
  (`/api/library`, orval `baseUrl: ''`), which the browser resolves against the page origin.
  Inside the container that origin is the bundle itself, so every call would look for the API
  in the packaged assets. The native build needs an absolute base URL — a `VITE_API_BASE_URL`
  read by `shared/apiClient.ts` is enough, empty by default so the web is untouched — and the
  API needs its `CORS_ORIGINS` (`apps/api/src/main/resources/application.properties`, wired
  through `infra/helm/librarius/templates/api.yaml`) to accept `https://localhost` and
  `capacitor://localhost`.
- **Safe areas and the status bar.** `index.html` already carries `viewport-fit=cover`, but
  no rule reads `env(safe-area-inset-*)`, so the bottom navigation would sit under the
  gesture bar. The fix belongs with the native project: Capacitor 7 can handle Android 15
  edge-to-edge itself (`android.adjustMarginsForEdgeToEdge`), and that decision determines
  whether the insets reach the CSS at all. Deliberately left to
  [#70](https://github.com/zelytra/Librarius/issues/70) rather than guessed at here.

## 7. Continuous integration

`.github/workflows/mobile.yml` runs on any change to `apps/mobile/**` or `apps/web/**`:
install, `typecheck`, then `pnpm mobile:build`. It needs no SDK and no emulator, and takes
about as long as the web build. The Android build itself is
[#70](https://github.com/zelytra/Librarius/issues/70)'s job.

Adding the workspace does **not** change the web image build: `apps/web/Dockerfile` copies
only `apps/web/package.json` into its context, and `pnpm install --frozen-lockfile` accepts
a workspace member that is absent from the context — verified by building the image.
