# Architecture

Librarius is four pieces behind one PWA: a **web** app, an **api**, a **database**, and
**Keycloak** for authentication. This page explains what each one is and why it is built the
way it is; the full picture, including the parts still being built, lives in
[`docs/ARCHITECTURE.md`](https://github.com/zelytra/Librarius/blob/main/docs/ARCHITECTURE.md),
which is updated in the same pull request as any structural change.

## The four layers

| Layer | Technology | Why |
|---|---|---|
| Web | React + Vite + TypeScript, installable PWA | One responsive codebase serves desktop and mobile, and it is what the native mobile shell (below) wraps |
| API | Java + Quarkus | Fast startup, metrics (Micrometer/Prometheus) and OIDC support built in rather than bolted on |
| Database | PostgreSQL, through Hibernate Panache and Flyway | Every schema change is a versioned migration — see [Data model](https://github.com/zelytra/Librarius/wiki/Data-Model) |
| Auth | Keycloak (OIDC) | No home-grown sign-up/reset/refresh flow to maintain, and the same login also serves Grafana |

The web app never talks to the database or to Keycloak's admin API directly — it calls the
Quarkus API over `/api`, authenticating with the OIDC token Keycloak issued it. The API is
the only thing that reads or writes PostgreSQL, and every one of its resources is scoped to
the caller: filtered on their identifier, so one user's data is never reachable through
another user's session.

The front end and back end share a contract rather than two hand-maintained copies of it:
the API generates an OpenAPI schema at build time
([`openapi/`](https://github.com/zelytra/Librarius/tree/main/openapi)), and
[orval](https://orval.dev/) turns it into typed React Query hooks the web app calls. A CI
job fails the build if someone changes an endpoint and forgets to regenerate the client.

## Repository layout

```text
apps/
  web/        React + Vite + TS PWA
  api/        Quarkus API (Maven)
  mobile/     Capacitor shell: no application code, wraps the web build for Android/iOS
openapi/      The contract above: generated by the api, consumed by the web app
packages/     Reserved for shared libraries — empty to date, the workspace glob expects it
infra/        Local and production docker compose, the Keycloak realm, Prometheus, Grafana,
              and the Helm chart used to deploy to Kubernetes
e2e/          Playwright suite exercising the real stack end to end
docs/         This project's public documentation (architecture, deployment)
.claude/docs/ Detailed working documentation, for whoever — human or agent — picks up a task
```

`apps/web` and `apps/mobile` are pnpm workspaces; `apps/api` is a Maven project pnpm leaves
alone. CI keeps the two toolchains apart with path filters, so a front-end-only change never
waits on a Maven build, and vice versa.

## The mobile shell

`apps/mobile` is a [Capacitor](https://capacitorjs.com/) container with no screens of its
own: it packages the exact same `apps/web` build for Android and iOS, so there is one set of
screens to maintain, not two codebases to keep in sync. It is early: no native project has
been generated yet, and sign-in does not work inside the container yet — see
[`.claude/docs/MOBILE.md`](https://github.com/zelytra/Librarius/blob/main/.claude/docs/MOBILE.md)
for exactly where that effort stands.

## CI/CD, briefly

Every pull request runs linting, type-checking, both test suites and a build. A merge into
`main` builds and deploys to the staging environment, and a `vX.Y.Z` tag cuts a release
without deploying it — production is not open yet. The
[Deployment](https://github.com/zelytra/Librarius/wiki/Deployment) page picks this up in
more detail, and
[`docs/ARCHITECTURE.md`](https://github.com/zelytra/Librarius/blob/main/docs/ARCHITECTURE.md)
lists every workflow.
